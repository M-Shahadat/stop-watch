# Stopwatch

A personal task time tracker with start, pause, resume, stop, edit, delete, categories, category totals, and day-by-day weekly and monthly history in the viewer's time zone. The interface works on desktop and phone screens.

## Stack

- Next.js 16 and React for the static frontend
- FastAPI and SQLAlchemy for the API
- PostgreSQL for persistent tasks, categories, and running intervals
- One Docker web service for both the frontend and API

The frontend calls `/api` on its own origin. In development, Next.js proxies `/api` to FastAPI on port 8000. In production, FastAPI serves the exported frontend and API together. No browser-facing API URL or CORS configuration is needed.

## Local development

1. Create a PostgreSQL database (Neon is one option). Copy `backend/.env.example` to `backend/.env` and set `DATABASE_URL`.
2. Start the API:

   ```sh
   cd backend
   python3 -m venv .venv
   .venv/bin/pip install -r requirements.txt
   .venv/bin/uvicorn app.main:app --reload
   ```

3. In another terminal, start the frontend:

   ```sh
   cd frontend
   npm ci
   npm run dev
   ```

Open `http://localhost:3000`. The API docs are at `http://localhost:8000/docs`. To try the sign-in flow locally, set `APP_PASSWORD` and `APP_SESSION_SECRET` in `backend/.env` and restart the API. Without them, local development skips sign-in.

## Deploy on Render

The repository includes `Dockerfile` and `render.yaml` for a single Render web service. Render [supports Docker web services](https://render.com/docs/docker) and [Blueprint environment variables](https://render.com/docs/configure-environment-variables).

1. Push this directory to a GitHub repository. The root `.gitignore` excludes local `.env` files and build output. Check the repository contents before pushing.
2. In Render, choose **New → Blueprint**, connect the repository, and apply `render.yaml`.
3. Enter `DATABASE_URL` and a long, unique `APP_PASSWORD` in Render. `APP_SESSION_SECRET` is generated by the Blueprint. Use a PostgreSQL connection URL that requires TLS.
4. Wait for the health check to pass, then open the generated `onrender.com` URL on your phone and sign in. Keep the password in a password manager.

The application refuses to start in production without a password and session secret. The API uses an HttpOnly, Secure, SameSite cookie; credentials are never built into the frontend. Render's free web services [spin down after 15 minutes without traffic](https://render.com/docs/free), and waking them can take about a minute. The app retries read requests and keeps the connection screen open while the service wakes. For an always-on app, change the web service to a [paid compute plan](https://render.com/docs/compute-plans) in Render and update the `plan` value in `render.yaml` before syncing the Blueprint again.

### Keep the free Render service awake with GitHub Actions

The included workflow requests the service's `/health` endpoint every five minutes using the GitHub account that hosts this repository. After pushing this workflow, go to **GitHub → repository Settings → Secrets and variables → Actions → Variables → New repository variable**. Set `RENDER_HEALTH_URL` to `https://YOUR-SERVICE.onrender.com/health` (replace the hostname with your actual Render URL). The job is skipped until that variable is set. You can use **Actions → Keep Render awake → Run workflow** to test it.

This is most suitable for a public repository, where standard GitHub-hosted Actions runners are free. In a private repository, frequent runs can exhaust the included Actions minutes. GitHub can delay or drop scheduled runs and disables scheduled workflows in public repositories after 60 days without repository activity, so occasional Render cold starts are still possible. Keeping the Render service active also uses nearly all of its 750 free instance hours in a 31-day month.

## Data and migrations

Startup creates missing tables and adds the existing category and pause columns when needed. Active intervals are saved when a task is paused or stopped, so daily, weekly, and monthly views can split time across local midnight. Older tasks have no interval history; their previously recorded time is assigned to their start date. Edited completed time is assigned to the stop date, with subtractions taken from the latest day first. For longer-term production use, replace the startup SQL with versioned migrations before changing the schema again.
